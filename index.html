Q-Learning Robot
Project Walkthrough

This page assumes you have zero prior context on this project, and starts from "what am I actually being asked to do." It covers what the task is, how the map and actions are defined, how the reward is calculated, how Q-learning differs from Dyna-Q, and what each file in the project is responsible for.

1 · What this project is actually about

This is project 7 of 8 in ML4T: the course builds a "machine learning for trading" system step by step. The earlier projects were supervised learning (decision trees, regression learners); this one switches to reinforcement learning — instead of "here's a pile of labeled data, go fit it," it's "here's an environment you can interact with; try things, accumulate experience, and gradually learn what to do."

To get the algorithm itself right first, the assignment doesn't jump straight into trading. Instead you practice on a simplified grid-world navigation problem: a robot stands on a 10×10 grid containing open floor, obstacles, quicksand (a big penalty for stepping on it), and one goal cell. At each step the robot can only choose one of 4 actions (move one cell north/east/south/west). You write a "brain" (the QLearner class) that learns, through repeated trial and continuous updating of its own judgment, a path that earns the highest total reward.

The assignment text calls out one key line: "your Q-Learning code really shouldn't care what specific problem it's solving" — QLearner only deals with abstract integer state, integer action, and floating-point reward. It has no idea what "grid," "quicksand," or "goal" mean. The piece that actually knows those concepts is testqlearner.py: it translates "which row/column the robot is on" into an integer state fed to the learner, and translates the integer action the learner returns back into "which direction to move." This division of labor — "the environment handles translation, the brain only understands abstract numbers" — is the same idea as the "agent / environment interface separation" used throughout reinforcement learning engineering. Later, Project 8 plugs the exact same QLearner class into a completely different environment — stock trading — unchanged, relying on exactly this decoupling.

How the reward is calculated

SituationRewardNotes
Normally moves to a floor cell / any cell other than the goal-1The "time cost" of each step, which encourages reaching the goal quickly
The intended direction goes out of bounds, or hits an obstacle (1)-1The action is judged illegal; the robot stays in place, but still pays the cost
Steps onto quicksand (5 or 6)-100A heavy penalty that forces the policy to learn to avoid quicksand, even when it looks "closer to the goal"
Reaches the goal (3)+1Reaching it counts as success; the robot is immediately sent back to the start and a new epoch begins
An easy-to-miss detail: on every step, the robot has a 20% chance of "disobeying" — regardless of which direction QLearner chose, the direction actually executed gets replaced with a random one (rand.uniform(0,1) <= 0.20 triggers this "go rogue" behavior). This randomness is completely invisible to the learner: it never sees whether a given step was randomly overridden — it only ever sees the final (s, a, s_prime, r) tuple. This is exactly what "model-free" means, which section 3 covers next.

3 · Q-learning (model-free) vs Dyna-Q (adds a model-based component)

If you've done a project that solves an MDP with value iteration: that approach needs to know the state transition probabilities P(s'|s,a) and the reward function ahead of time, and the planner uses this "known world model" directly to compute expected costs. Q-learning takes a completely different approach — it doesn't know, and doesn't need to know, what the environment's transition probabilities and reward function look like. It can only estimate Q[s,a] (the long-term value of taking action a in state s) gradually, through repeated real experience of the form "I took action a, and observed new state s' and reward r." That's what "model-free" means: the model (the environment's rules) is a black box to the algorithm.

Pure Q-learning (dyna=0)Dyna-Q (dyna=200)
Q-table updates per query() call1 (uses only this step's real experience)1 real update + 200 "replay" updates
Where the replay data comes from—Every real experience (s,a,s',r) is stored in the self.model list; replay randomly samples past experiences and re-runs the update, with no new real interaction with the environment
PurposeNeeds many real query() calls before the Q-table convergesUses "remembering" instead of "re-experiencing" to approach convergence with fewer real calls — note that what speeds up is the number of query() calls needed to converge, not wall-clock time (which is actually slower, since each step does 200x more computation)
How this project grades it10 maps, 500 epochs each, requires total reward ≥ 1.5× the reference solutionOnly tests world01/world02, 50 epochs each, same requirement of ≥ 1.5× the reference solution (comparing "500 epochs without Dyna" vs "50 epochs with Dyna" is specifically testing whether Dyna actually speeds up convergence)
The assignment's technical requirements explicitly state: "you may not cut corners to reduce the effect of Dyna" — for example, you can't do only the first few replays, or replay only every N steps to save work. for _ in range(self.dyna) inside query() honestly runs the full dyna replays every time, satisfying this requirement.
